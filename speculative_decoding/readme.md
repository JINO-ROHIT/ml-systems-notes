## notes on speculative decoding

inference in the decoding phase is usually slow compared to the prefill phase due to its serial nature doing it one by one.

1. it has low inter token latency and llm inference is memory bound.
2. some tokens are way easier to predict compared to others.


speculative decoding changes this paradigm. the workflow roughly looks like this -
1. the draft model (10x smaller) performs N consecutive inferences to generate N candidate tokens. although this process is sequential, it is very fast because the model is extremely small.
2. the target model inputs all N draft tokens at once and calculates the probability distribution of these N positions with just one forward pass.
3. there are three things that can happen here - 
- full match - the large model approves all drafts, and this round directly produces N+1 tokens (including one generated by the large model itself).
- prefix match - the longest prefix is accepted and maybe towards the end, the tokens changed and become different , so they are discarded. 
- no match - the first tokens was wrong and the entire sequence is dropped.


we have two models:
- `Mq`: the small draft model. this is cheap and fast.
- `Mp`: the large target/verifier model. this is the model whose output distribution we actually want.

### acceptance rule/verification

instead of checking for simply equality, we use a rejection sampling rule -

```
alpha = min(1, p(x)/q(x)) 
```

say draft model assigns 0.4 and target model assigns 0.8.

then 0.8/0.4 = 2
alpha = min(1, 2) = 1 (always accept)

target model likes this token unlike draft.

along with this, during verification, each candidate token generated gets its own random number drawn from uniform distribution basically pick a random number from 0 to 1.

```
u ~ uniform(0, 1)
```

why do we need this? id think of alpha as accept this draft token with a probability of alpha. for the case 1 its very clear. what about something like 50%?
we generate this random number.

say our u = 0.75
        alpha = 0.25
    
alpha < u, reject this token.

exactly 25% of the time, a uniformly random number will fall below 0.25, so only then the token is accepted.

why dont we reject whenever p < q?

consider a case where draft = 0.40 and target = 0.39.
the models are almost identical. but if you always rejected whenever p < q, you always reject this token 100% of the time.

### correction and sampling

this happens at the end of the verification phase is done.

1. all tokens are accepted - say we accepted all the tokens, in that case, as a reward the target predicts the final token due its normal autoregressive nature. so the final tokens generated are actually N + 1.

2. for the first rejected token, we need to still generate the last token after the rejected Nth token.

consider we have -

egypt won the world cup.

target accepts "egypt" and rejects the word "won".

so the sequence is "egypt", what should the next word be? do another forward pass? nah too much computation.

you already have the target distribution sampled from the first forward pass, we need need to adjust this after dropping the rejected tokens distribution.

say, my distribution was 

won 80%
lost 10%
drew 10%

once you drop won, we need to adjust this so the probabiliyy sums to 1 yeah.
we take all the probability mass removed from won and resdistribute to the tokens the target prefers using `max(0, p−q)`


### acceleration effect

speculative decoding is faster because it reduces the number of serial calls to the large model.

without speculative decoding, generating `K` tokens needs `K` separate target model decode steps:

```text
large model -> token 1
large model -> token 2
large model -> token 3
```

with speculative decoding, the draft model generates `K` tokens cheaply, and the large model verifies them in one batched forward pass:

```text
small model -> K draft tokens
large model -> verify K positions in parallel
```

the compute done by the large model is not free, but the hardware utilization is much better. decode is usually memory bandwidth bound because every step loads the model weights to produce only one token. verifying multiple tokens in one pass improves the compute-to-memory ratio.

the speedup depends on a few things:

- `K`: how many draft tokens we try per iteration.
- how close `q` is to `p`: if the draft model behaves like the target model, more tokens get accepted.
- the cost ratio between `Mq` and `Mp`: the draft model must be much cheaper than the target model.

there is a tradeoff with `K`. larger `K` gives the system more chances to accept many tokens in one verifier call, but if `K` is too large and the draft model is not close enough to the target model, many of those tokens will be rejected.

another way to think about it:

```text
speedup comes from accepted draft tokens per target model call
```

if the draft model is weak, the target model keeps rejecting early and the speedup is small. if the draft model is strong enough, the verifier accepts longer prefixes and the serial decoding loop becomes much shorter.


some things to watch out for 

1. memory overhead since we are loading two models now
2. if the tokens generated are being rejected too much, its actually a slowdown.
3. get the draft model to match the distribution very well with the verifier model. 


### some popular techniques

1. medusa - lets not train an indepedent draft model, but attach multiple lightweight mlp prediction heads on top of the llm to predict subsequent tokens in parallel, and propose a tree attention mechanism to simultaneously validate multiple candidate links. the drawbacks are - 
- each prediction head works independently, ignoring the dependencies between positions, resulting in limited prediction accuracy (approximately 0.6), 
- and the accuracy drops sharply with increasing prediction distance.
